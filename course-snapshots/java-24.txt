PLACEMENT · LEVEL 24</p><h1>Testing, Debugging &amp; Placement Projects</h1><p class="lead">Finish the course by designing testable code, debugging from evidence and presenting production-minded projects in interviews.</p><div class="lesson-meta"><span>Level 24 of 24</span><span>Placement ready</span><span>240–360 minutes</span><span>8 concept checks</span></div></div><aside class="outcome-card"><span>BY THE END, YOU CAN</span><h2>Ship and explain a complete Java solution</h2><ul><li>Design focused automated tests.</li><li>Use debugger and logs systematically.</li><li>Refactor with confidence.</li><li>Structure portfolio projects.</li><li>Answer placement questions with evidence.</li></ul></aside></section><nav class="jump-bar"><a href="#concepts">Concepts</a><a href="#examples">Examples</a><a href="#trace">Trace</a><a href="#revision">Revision</a><a href="#interview">Interview</a><a href="#practice">Practice</a><a href="#quiz">Check</a></nav><section class="lesson-section" id="concepts"><header class="section-heading"><span>CONCEPTS · MECHANISMS · TRADE-OFFS</span><h2>Testing, Debugging &amp; Placement Projects: Mental Models and Practice</h2><p>Learn the mechanism first, then use the API with clear assumptions, boundaries and tests.</p></header><article class="concept-block"><h3>1. Testing strategy</h3><p>A good unit test names one behaviour, arranges minimal state, performs one meaningful action and asserts observable results. Test contracts and boundaries rather than private implementation.</p><p>Use integration tests for database, filesystem and framework wiring; use end-to-end tests sparingly for critical user journeys. A test pyramid is guidance, not a quota.</p><div class="concept-table-wrap"><table class="concept-table"><thead><tr><th>Layer</th><th>Confidence</th><th>Cost</th></tr></thead><tbody><tr><td>Unit</td><td>Local logic</td><td>Fast and isolated</td></tr><tr><td>Integration</td><td>Components and infrastructure</td><td>Moderate</td></tr><tr><td>End-to-end</td><td>Deployed user flow</td><td>Slow and broad</td></tr><tr><td>Static analysis</td><td>Rule violations</td><td>Very fast</td></tr></tbody></table></div></article><article class="concept-block"><h3>2. Debugging from evidence</h3><p>Reproduce the smallest failing case, record expected versus actual behaviour, inspect the first divergence, form one hypothesis and run one discriminating experiment.</p><p>Use conditional breakpoints, watches, stack frames and structured logs. Do not change several unrelated lines before learning which assumption failed.</p><div class="concept-note"><strong>Important:</strong> A stack trace is a call history, not noise. Read exception type, message, first relevant application frame and cause chain.</div></article><article class="concept-block"><h3>3. Clean delivery</h3><p>Separate domain rules from input/output so core behaviour can be tested without console, web or database infrastructure. Keep methods cohesive and dependencies explicit.</p><p>Use a build tool, version control, reproducible configuration, README setup, automated tests and CI. Never commit credentials; load secrets from deployment configuration.</p></article><article class="concept-block"><h3>4. Placement portfolio</h3><p>A strong project demonstrates a real problem, documented requirements, architecture decisions, data model, validation, failure handling, tests, deployment and measured limitations.</p><p>Be ready to trace one feature end to end and justify trade-offs. Honest scope plus evidence is stronger than a long technology list.</p><ul><li>Student/placement management with JDBC transactions and role-based operations.</li><li>Concurrent job scheduler with bounded queues, cancellation and metrics.</li><li>Expense analytics CLI with NIO import, validation and Stream reports.</li><li>Library service with clean domain layer, repository contract and automated tests.</li></ul></article></section><section class="lesson-section" id="examples"><header class="section-heading"><span>RUNNABLE JAVA</span><h2>Examples Worth Tracing</h2><p>Predict the result before running each program. Then change one value and explain the new behaviour.</p></header><article class="example-card"><header><div><span>EXAMPLE 01</span><h3>Tiny dependency-free test harness</h3></div><button class="copy-code" type="button" data-copy-example="0">Copy code</button></header><div class="code-wrap"><pre><code>public class Program {
    static int fee(int units){if(units&lt;0)throw new IllegalArgumentException();return units&lt;=100?units*2:200+(units-100)*3;}
    static void check(String name,int expected,int actual){if(expected!=actual)throw new AssertionError(name+&quot;: expected &quot;+expected+&quot;, got &quot;+actual);}
    public static void main(String[] args){check(&quot;boundary&quot;,200,fee(100));check(&quot;next slab&quot;,203,fee(101));System.out.println(&quot;2 tests passed&quot;);}
}</code></pre></div><footer>Production projects should use JUnit, but this compilable example exposes the anatomy of named boundary assertions without external dependencies.<pre>Output:
2 tests passed</pre></footer></article><article class="example-card"><header><div><span>EXAMPLE 02</span><h3>Inject a repository for testability</h3></div><button class="copy-code" type="button" data-copy-example="1">Copy code</button></header><div class="code-wrap"><pre><code>import java.util.*;
public class Program {
    interface UserRepository{Optional&lt;String&gt; find(int id);}
    static class GreetingService{private final UserRepository repo;GreetingService(UserRepository r){repo=r;}String greet(int id){return repo.find(id).map(n-&gt;&quot;Hello, &quot;+n).orElse(&quot;User not found&quot;);}}
    public static void main(String[] args){UserRepository fake=id-&gt;id==7?Optional.of(&quot;Asha&quot;):Optional.empty();System.out.println(new GreetingService(fake).greet(7));}
}</code></pre></div><footer>The service depends on a small contract, so a deterministic fake tests the domain path without a database.<pre>Output:
Hello, Asha</pre></footer></article></section><section class="lesson-section" id="trace"><header class="section-heading"><span>INTERACTIVE LEARNING · PROGRAM TRACE</span><h2>Trace an evidence-based class="section-heading"><span>INTERVIEW QUESTIONS</span><h2>Explain, Do Not Memorize</h2><p>Open each answer only after speaking your own version aloud.</p></header><div class="interview-list"><details><summary>1. Unit versus integration test?</summary><p>A unit test isolates focused logic; an integration test verifies collaboration with real components such as a database, filesystem or framework.</p></details><details><summary>2. What makes code testable?</summary><p>Cohesive functions, explicit dependencies, separated side effects, deterministic inputs and observable results.</p></details><details><summary>3. How do you debug an intermittent bug?</summary><p>Capture environment, inputs, timing and correlation data; add focused observability, test concurrency assumptions and reduce the failing scenario.</p></details><details><summary>4. How should a project be explained?</summary><p>Start with problem and users, then requirements, architecture, one traced feature, trade-offs, validation, tests, deployment and next limitations.</p></details><details><summary>5. What belongs in a Java project README?</summary><p>Purpose, prerequisites, setup, configuration, run/test commands, architecture summary, sample flows, limitations and safe secret handling.</p></details></div></section><section class="lesson-section" id="practice"><header class="section-heading"><span>PROGRAMMING PROBLEMS</span><h2>Apply the Concept Independently</h2><p>Use the CodeBhavya online compiler. follow-ups.</p><details><summary>Show guidance</summary><p>Use concrete decisions and measured results.</p></details></article></div></section><section class="lesson-section" id="quiz"><header
