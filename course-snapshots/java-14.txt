CORE LIBRARIES · LEVEL 14</p><h1>Exception Handling</h1><p class="lead">Represent failures with precise exception contracts, preserve causes and close resources reliably.</p><div class="lesson-meta"><span>Level 14 of 24</span><span>Intermediate</span><span>110–150 minutes</span><span>8 concept checks</span></div></div><aside class="outcome-card"><span>BY THE END, YOU CAN</span><h2>Design failure paths that remain diagnosable</h2><ul><li>Distinguish checked and unchecked exceptions.</li><li>Use try/catch/finally.</li><li>Apply try-with-resources.</li><li>Create meaningful domain exceptions.</li><li>Preserve root causes.</li></ul></aside></section><nav class="jump-bar"><a href="#concepts">Concepts</a><a href="#examples">Examples</a><a href="#trace">Trace</a><a href="#revision">Revision</a><a href="#interview">Interview</a><a href="#practice">Practice</a><a href="#quiz">Check</a></nav><section class="lesson-section" id="concepts"><header class="section-heading"><span>CONCEPTS · MECHANISMS · TRADE-OFFS</span><h2>Exception Handling: Mental Models and Practice</h2><p>Learn the mechanism first, then use the API with clear assumptions, boundaries and tests.</p></header><article class="concept-block"><h3>1. Failure taxonomy</h3><p>Checked exceptions must be caught or declared and often represent recoverable external failures. RuntimeException subclasses usually represent violated preconditions, invalid state or programming defects.</p><p>Errors describe serious JVM or environment conditions and are generally not application recovery mechanisms.</p><div class="concept-table-wrap"><table class="concept-table"><thead><tr><th>Kind</th><th>Compiler rule</th><th>Typical meaning</th></tr></thead><tbody><tr><td>Checked Exception</td><td>Catch or declare</td><td>External/recoverable failure</td></tr><tr><td>RuntimeException</td><td>No declaration required</td><td>Contract/programming failure</td></tr><tr><td>Error</td><td>No declaration required</td><td>Serious runtime condition</td></tr></tbody></table></div></article><article class="concept-block"><h3>2. Catch at the right boundary</h3><p>Catch only when the current layer can recover, translate or add meaningful context. A broad catch that prints and continues can corrupt later behaviour.</p><p>Order catches from specific to general. Preserve the original throwable as the cause when translating between abstraction layers.</p></article><article class="concept-block"><h3>3. Resources and cleanup</h3><p>Try-with-resources closes AutoCloseable resources in reverse declaration order, even when work fails.</p><p>If both work and close fail, the work exception remains primary and close failures become suppressed exceptions, preserving evidence.</p><div class="concept-note"><strong>Important:</strong> Never use an empty catch block. At minimum, enforce a defined recovery or propagate context.</div></article></section><section class="lesson-section" id="examples"><header class="section-heading"><span>RUNNABLE JAVA</span><h2>Examples Worth Tracing</h2><p>Predict the result before running each program. Then change one value and explain the new behaviour.</p></header><article class="example-card"><header><div><span>EXAMPLE 01</span><h3>Translate while preserving cause</h3></div><button class="copy-code" type="button" data-copy-example="0">Copy code</button></header><div class="code-wrap"><pre><code>public class Program {

    }
    public static void main(String[] args){try{parsePort(&quot;abc&quot;);}catch(IllegalArgumentException e){System.out.println(e.getMessage());}}
}</code></pre></div><footer>The public method reports domain context and retains NumberFormatException as the cause.<pre>Output:

id="interview"><header class="section-heading"><span>INTERVIEW QUESTIONS</span><h2>Explain, Do Not Memorize</h2><p>Open each answer only after speaking your own version aloud.</p></header><div class="interview-list"><details><summary>1. Checked versus unchecked?</summary><p>Checked exceptions participate in compile-time handling; unchecked RuntimeExceptions do not. The design distinction is expected recovery versus contract/programming failure.</p></details><details><summary>2. Does finally always execute?</summary><p>It normally executes when leaving try/catch, but not after abrupt JVM termination or certain fatal conditions.</p></details><details><summary>3. Why try-with-resources?</summary><p>It provides deterministic cleanup and preserves suppressed close failures correctly.</p></details><details><summary>4. throw versus throws?</summary><p>throw creates/propagates one throwable expression; throws declares possible checked exceptions in a method signature.</p></details><details><summary>5. Why preserve causes?</summary><p>The higher-level message explains context while the cause retains the original stack and failure detail.</p></details></div></section><section class="lesson-section" id="practice"><header class="section-heading"><span>PROGRAMMING PROBLEMS</span><h2>Apply the Concept Independently</h2><p>Use the CodeBhavya online compiler.
