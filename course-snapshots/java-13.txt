OBJECT-ORIENTED DESIGN · LEVEL 13</p><h1>Encapsulation, Packages &amp; Access</h1><p class="lead">Control dependency direction with access levels, packages, stable APIs and enforceable class boundaries.</p><div class="lesson-meta"><span>Level 13 of 24</span><span>Intermediate</span><span>110–150 minutes</span><span>8 concept checks</span></div></div><aside class="outcome-card"><span>BY THE END, YOU CAN</span><h2>Organize Java code into maintainable boundaries</h2><ul><li>Apply all access levels.</li><li>Design package responsibilities.</li><li>Expose minimal APIs.</li><li>Use imports correctly.</li><li>Recognize modules as stronger boundaries.</li></ul></aside></section><nav class="jump-bar"><a href="#concepts">Concepts</a><a href="#examples">Examples</a><a href="#revision">Revision</a><a href="#interview">Interview</a><a href="#practice">Practice</a><a href="#quiz">Check</a></nav><section class="lesson-section" id="concepts"><header class="section-heading"><span>CONCEPTS · MECHANISMS · TRADE-OFFS</span><h2>Encapsulation, Packages &amp; Access: Mental Models and Practice</h2><p>Learn the mechanism first, then use the API with clear assumptions, boundaries and tests.</p></header><article class="concept-block"><h3>1. Access is design</h3><p><code>private</code> limits access to the declaring class; package-private to the package; <code>protected</code> adds subclass access; <code>public</code> exposes an API wherever the type is accessible.</p><p>Choose the narrowest access that satisfies collaborators. Hiding representation preserves freedom to change it.</p><div class="concept-table-wrap"><table class="concept-table"><thead><tr><th>Modifier</th><th>Same class</th><th>Same package</th><th>Subclass elsewhere</th><th>Everywhere</th></tr></thead><tbody><tr><td>private</td><td>Yes</td><td>No</td><td>No</td><td>No</td></tr><tr><td>package-private</td><td>Yes</td><td>Yes</td><td>No</td><td>No</td></tr><tr><td>protected</td><td>Yes</td><td>Yes</td><td>Yes*</td><td>No</td></tr><tr><td>public</td><td>Yes</td><td>Yes</td><td>Yes</td><td>Yes</td></tr></tbody></table></div></article><article class="concept-block"><h3>2. Package cohesion</h3><p>A package should group types that change for related reasons, not merely every controller or every utility in an application.</p><p>The package declaration must reflect deployment structure. Imports shorten type names but do not include code or change accessibility.</p></article><article class="concept-block"><h3>3. API and module boundaries</h3><p>Public APIs should expose domain abstractions, validate inputs and avoid leaking mutable implementation collections.</p><p>The Java module system can declare required modules and exported packages. Unexported packages remain strongly encapsulated from other named modules.</p><div class="concept-note"><strong>Important:</strong> Getters and setters do not automatically create encapsulation; a setter that accepts any state may destroy it.</div></article></section><section class="lesson-section" id="examples"><header class="section-heading"><span>RUNNABLE JAVA</span><h2>Examples Worth Tracing</h2><p>Predict the result before running each program. Then change one value and explain the new behaviour.</p></header><article class="example-card"><header><div><span>EXAMPLE 01</span><h3>Package-owned validation</h3></div><button class="copy-code" type="button" data-copy-example="0">Copy code</button></header><div class="code-wrap"><pre><code>public class Program {
    static final class Score{
        private final int value;
        private Score(int value){this.value=value;}
        static Score of(int value){if(value&lt;0||value&gt;100)throw new IllegalArgumentException();return new Score(value);}
        int value(){return value;}
    }
    public static void main(String[] args){System.out.println(Score.of(84).value());}
}</code></pre></div><footer>The private constructor forces clients through a validating factory, so invalid Score objects cannot be created.<pre>Output:
84</pre></footer></article><article class="example-card"><header><div><span>EXAMPLE 02</span><h3>Return an immutable view</h3></div><button class="copy-code" type="button" data-copy-example="1">Copy code</button></header><div class="code-wrap"><pre><code>import java.util.*;
public class Program {
    static class Roster{
        private final List&lt;String&gt; names=new ArrayList&lt;&gt;();
        void add(String name){names.add(Objects.requireNonNull(name));}
        List&lt;String&gt; names(){return List.copyOf(names);}
    }
    public static void main(String[] args){Roster r=new Roster();r.add(&quot;Isha&quot;);System.out.println(r.names());}
}</code></pre></div><footer>The returned list cannot mutate the internal ArrayList, preserving ownership.<pre>Output:
[Isha]</pre></footer></article></section><section class="lesson-section" id="revision"><header class="section-heading"><span>QUICK REVISION</span><h2>Recall the Essential Ideas</h2></header><div class="revision-grid"><div><b>01</b> Use the narrowest sufficient access.</div><div><b>02</b> Package-private is the default with no modifier.</div><div><b>03</b> Imports shorten names, not permissions.</div><div><b>04</b> Packages should be cohesive.</div><div><b>05</b> Public APIs must not leak mutable internals.</div><div><b>06</b> Modules can strongly encapsulate packages.</div></div></section><section class="lesson-section" id="interview"><header class="section-heading"><span>INTERVIEW QUESTIONS</span><h2>Explain, Do Not Memorize</h2><p>Open each answer only after speaking your own version aloud.</p></header><div class="interview-list"><details><summary>1. What is default access?</summary><p>When no member modifier is written, access is limited to the same package; it is called package-private.</p></details><details><summary>2. Is a getter always good encapsulation?</summary><p>No. Exposing mutable state or meaningless setters leaks representation and invariants.</p></details><details><summary>3. Protected versus package-private?</summary><p>Protected includes same-package access plus constrained subclass access across packages; package-private is package only.</p></details><details><summary>4. What does import do?</summary><p>It lets source use a simple type name; it does not load code or bypass access checks.</p></details><details><summary>5. Package versus module?</summary><p>A package names and groups types; a module declares larger dependency and export boundaries across packages.</p></details></div></section><section class="lesson-section" id="practice"><header class="section-heading"><span>PROGRAMMING PROBLEMS</span><h2>Apply the Concept Independently</h2><p>Use the CodeBhavya online compiler. 02</span><h3>Immutable roster API</h3><p>Prevent mutation through returned collections.</p><details><summary>Show guidance</summary><p>Return snapshots or unmodifiable copies.</p></details></article><article class="practice-card"><span>PROBLEM 03</span><h3>Factory boundary</h3><p>Make direct construction private and validate named creation paths.</p><details><summary>Show guidance</summary><p>Use meaningful factory names.</p></details></article><article class="practice-card"><span>PROBLEM 04</span><h3>Access experiment</h3><p>Test each
