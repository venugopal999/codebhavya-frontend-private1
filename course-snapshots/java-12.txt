OBJECT-ORIENTED DESIGN · LEVEL 12</p><h1>Polymorphism, Abstraction &amp; Interfaces</h1><p class="lead">Program to stable contracts while runtime objects supply replaceable behaviour.</p><div class="lesson-meta"><span>Level 12 of 24</span><span>Intermediate</span><span>110–150 minutes</span><span>8 concept checks</span></div></div><aside class="outcome-card"><span>BY THE END, YOU CAN</span><h2>Design extensible behaviour behind small contracts</h2><ul><li>Explain dynamic dispatch.</li><li>Use abstract classes and interfaces.</li><li>Apply interface segregation.</li><li>Use default methods carefully.</li><li>Avoid unsafe downcasts.</li></ul></aside></section><nav class="jump-bar"><a href="#concepts">Concepts</a><a href="#examples">Examples</a><a href="#trace">Trace</a><a href="#revision">Revision</a><a href="#interview">Interview</a><a href="#practice">Practice</a><a href="#quiz">Check</a></nav><section class="lesson-section" id="concepts"><header class="section-heading"><span>CONCEPTS · MECHANISMS · TRADE-OFFS</span><h2>Polymorphism, Abstraction &amp; Interfaces: Mental Models and Practice</h2><p>Learn the mechanism first, then use the API with clear assumptions, boundaries and tests.</p></header><article class="concept-block"><h3>1. Polymorphic calls</h3><p>A base-typed reference can identify different implementations. The compiler checks members against the declared type; runtime dispatch selects the most specific override.</p><p>Fields and static methods are not dynamically dispatched in the same way, so do not hide them to simulate polymorphism.</p></article><article class="concept-block"><h3>2. Abstract class versus interface</h3><p>An abstract class can hold shared instance state and protected implementation. An interface defines a role and supports multiple implementation inheritance.</p><p>Choose the smallest contract clients require; large interfaces force unrelated implementations to depend on unused methods.</p><div class="concept-table-wrap"><table class="concept-table"><thead><tr><th>Feature</th><th>Abstract class</th><th>Interface</th></tr></thead><tbody><tr><td>Instance state</td><td>Yes</td><td>No instance fields</td></tr><tr><td>Constructors</td><td>Yes</td><td>No</td></tr><tr><td>Multiple inheritance</td><td>No</td><td>A class may implement many</td></tr><tr><td>Purpose</td><td>Shared base mechanism</td><td>Capability contract</td></tr></tbody></table></div></article><article class="concept-block"><h3>3. Defaults, casts and sealed choices</h3><p>Default interface methods evolve contracts but should not become a dumping ground for stateful logic. Conflicts must be resolved explicitly.</p><p>A downcast asks runtime to verify a more specific type and can fail. Prefer polymorphic methods; use pattern matching when type distinctions are truly part of the problem.</p></article></section><section class="lesson-section" id="examples"><header class="section-heading"><span>RUNNABLE JAVA</span><h2>Examples Worth Tracing</h2><p>Predict the result before running each program. Then change one value and explain the new behaviour.</p></header><article class="example-card"><header><div><span>EXAMPLE 01</span><h3>Polymorphic payment processing</h3></div><button class="copy-code" type="button" data-copy-example="0">Copy code</button></header><div class="code-wrap"><pre><code>public class Program {
    interface Payment{String pay(long paise);}
    static class Upi implements Payment{public String pay(long p){return &quot;UPI:&quot;+p;}}
    static class Card implements Payment{public String pay(long p){return &quot;CARD:&quot;+p;}}
    static void checkout(Payment method){System.out.println(method.pay(2500));}
    public static void main(String[] args){checkout(new Upi());checkout(new Card());}
}</code></pre></div><footer>Checkout depends on one capability and does not branch on concrete payment types.<pre>Output:
UPI:2500
CARD:2500</pre></footer></article><article class="example-card"><header><div><span>EXAMPLE 02</span><h3>Pattern matching for a closed value</h3></div><button class="copy-code" type="button" data-copy-example="1">Copy code</button></header><div class="code-wrap"><pre><code>public class Program {
    static String describe(Object value){
        if(value instanceof String text) return &quot;text length &quot;+text.length();
        if(value instanceof Integer number) return &quot;integer &quot;+number;
        return &quot;other&quot;;
    }
    public static void main(String[] args){System.out.println(describe(&quot;Java&quot;));}
}</code></pre></div><footer>The pattern variable is in scope only where the type test succeeded; ordinary behaviour polymorphism should still use methods.<pre>Output:
text length 4</pre></footer></article></section><section class="lesson-section" id="trace"><header class="section-heading"><span>INTERACTIVE LEARNING · PROGRAM TRACE</span><h2>Trace interface after speaking your own version aloud.</p></header><div class="interview-list"><details><summary>1. Compile-time versus runtime polymorphism?</summary><p>Overloading is resolved at compile time; overriding is dynamically dispatched at runtime.</p></details><details><summary>2. Can an interface have methods with bodies?</summary><p>Yes: default, static and private helper methods, but it has no per-instance fields.</p></details><details><summary>3. Why program to an interface?</summary><p>Clients depend on a stable capability while implementations can be substituted and tested independently.</p></details><details><summary>4. What is interface segregation?</summary><p>Clients should not depend on methods they do not use; prefer focused role interfaces.</p></details><details><summary>5. Why avoid downcasting?</summary><p>It couples clients to implementations and may throw ClassCastException; a polymorphic operation is usually safer.</p></details></div></section><section class="lesson-section" id="practice"><header class="section-heading"><span>PROGRAMMING PROBLEMS</span><h2>Apply the Concept Independently</h2><p>Use the CodeBhavya online compiler.
