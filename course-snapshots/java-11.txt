OBJECT-ORIENTED DESIGN · LEVEL 11</p><h1>Inheritance &amp; Composition</h1><p class="lead">Reuse behaviour without weakening contracts; prefer composition when the relationship is capability rather than true substitutability.</p><div class="lesson-meta"><span>Level 11 of 24</span><span>Intermediate</span><span>110–150 minutes</span><span>8 concept checks</span></div></div><aside class="outcome-card"><span>BY THE END, YOU CAN</span><h2>Choose safe reuse relationships</h2><ul><li>Model is-a and has-a.</li><li>Apply substitutability.</li><li>Use super and protected carefully.</li><li>Recognize fragile inheritance.</li><li>Delegate through composition.</li></ul></aside></section><nav class="jump-bar"><a href="#concepts">Concepts</a><a href="#examples">Examples</a><a href="#trace">Trace</a><a href="#revision">Revision</a><a href="#interview">Interview</a><a href="#practice">Practice</a><a href="#quiz">Check</a></nav><section class="lesson-section" id="concepts"><header class="section-heading"><span>CONCEPTS · MECHANISMS · TRADE-OFFS</span><h2>Inheritance &amp; Composition: Mental Models and Practice</h2><p>Learn the mechanism first, then use the API with clear assumptions, boundaries and tests.</p></header><article class="concept-block"><h3>1. Subtype contract</h3><p>Inheritance creates a subtype promise: wherever the base type is expected, the subtype must preserve its observable contract.</p><p>A convenient code-reuse relationship is not enough; weakened postconditions or stronger preconditions violate substitutability.</p></article><article class="concept-block"><h3>2. super and member rules</h3><p>A subclass constructor invokes a superclass constructor before its own fields initialize. <code>super(...)</code> must be first.</p><p>Private members remain encapsulated; protected broadens access to subclasses and same-package code and can create coupling to representation.</p></article><article class="concept-block"><h3>3. Composition and delegation</h3><p>Composition builds a type from collaborators and delegates work through small interfaces. It allows behaviour to vary without claiming an is-a relationship.</p><p>Prefer it when policies change independently, multiple capabilities combine, or base-class internals should remain hidden.</p><div class="concept-table-wrap"><table class="concept-table"><thead><tr><th>Question</th><th>Inheritance</th><th>Composition</th></tr></thead><tbody><tr><td>Relationship</td><td>is-a</td><td>has-a/uses-a</td></tr><tr><td>Binding</td><td>Base implementation hierarchy</td><td>Collaborator interface</td></tr><tr><td>Change risk</td><td>Fragile base coupling</td><td>Explicit delegation</td></tr><tr><td>Multiple behaviours</td><td>Single class inheritance</td><td>Many collaborators</td></tr></tbody></table></div></article></section><section class="lesson-section" id="examples"><header class="section-heading"><span>RUNNABLE JAVA</span><h2>Examples Worth Tracing</h2><p>Predict the result before running each program. Then change one value and explain the new behaviour.</p></header><article class="example-card"><header><div><span>EXAMPLE 01</span><h3>Compose a discount policy</h3></div><button class="copy-code" type="button" data-copy-example="0">Copy code</button></header><div class="code-wrap"><pre><code>public class Program {
    interface Discount{long apply(long paise);}
    static class Checkout{
        private final Discount discount;
        Checkout(Discount discount){this.discount=discount;}
        long total(long paise){return discount.apply(paise);}
    }
    public static void main(String[] args){Checkout c=new Checkout(p-&gt;p*90/100);System.out.println(c.total(5000));}
}</code></pre></div><footer>Checkout uses a policy rather than inheriting from a discount type; policies can change independently.<pre>Output:
4500</pre></footer></article><article class="example-card"><header><div><span>EXAMPLE 02</span><h3>Valid subtype override</h3></div><button class="copy-code" type="button" data-copy-example="1">Copy code</button></header><div class="code-wrap"><pre><code>public class Program {
    static class Message{String label(){return &quot;message&quot;;}}
    static class Alert extends Message{@Override String label(){return &quot;alert&quot;;}}
    public static void main(String[] args){Message m=new Alert();System.out.println(m.label());}
}</code></pre></div><footer>An Alert is usable through the Message contract, while dynamic dispatch selects its override.<pre>Output:
alert</pre></footer></article></section><section class="lesson-section" id="trace"><header class="section-heading"><span>INTERACTIVE LEARNING · PROGRAM TRACE</span><h2>Trace construction and dispatch</h2><p>Declared type controls access; Why favor composition?</summary><p>It exposes dependencies, combines multiple behaviours and avoids coupling to superclass implementation details.</p></details><details><summary>2. What is substitutability?</summary><p>Code written for a base contract should work correctly with every subtype without special-case knowledge.</p></details><details><summary>3. Are constructors inherited?</summary><p>No. A subclass invokes a superclass constructor but does not inherit constructors as members.</p></details><details><summary>4. What does protected mean?</summary><p>Access is available to same-package code and to subclasses under specific reference rules; it is wider than purely subclass-only access.</p></details><details><summary>5. What is fragile base-class risk?</summary><p>A base implementation change can break subclasses that depended on undocumented call order or protected internals.</p></details></div></section><section class="lesson-section" id="practice"><header class="section-heading"><span>PROGRAMMING PROBLEMS</span><h2>Apply the Concept Independently</h2><p>Use the CodeBhavya online compiler.
