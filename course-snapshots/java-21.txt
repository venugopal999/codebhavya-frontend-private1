PLACEMENT · LEVEL 21</p><h1>JVM Memory &amp; Garbage Collection</h1><p class="lead">Connect source-level objects and calls to class metadata, stack frames, heap reachability and measured performance.</p><div class="lesson-meta"><span>Level 21 of 24</span><span>Advanced</span><span>150–210 minutes</span><span>8 concept checks</span></div></div><aside class="outcome-card"><span>BY THE END, YOU CAN</span><h2>Diagnose memory behaviour with the right JVM model</h2><ul><li>Describe JVM runtime areas.</li><li>Trace reachability and collection eligibility.</li><li>Distinguish leaks from high allocation.</li><li>Understand JIT warm-up.</li><li>Use evidence-driven diagnostics.</li></ul></aside></section><nav class="jump-bar"><a href="#concepts">Concepts</a><a href="#examples">Examples</a><a href="#trace">Trace</a><a href="#revision">Revision</a><a href="#interview">Interview</a><a href="#practice">Practice</a><a href="#quiz">Check</a></nav><section class="lesson-section" id="concepts"><header class="section-heading"><span>CONCEPTS · MECHANISMS · TRADE-OFFS</span><h2>JVM Memory &amp; Garbage Collection: Mental Models and Practice</h2><p>Learn the mechanism first, then use the API with clear assumptions, boundaries and tests.</p></header><article class="concept-block"><h3>1. Runtime memory model</h3><p>Each thread owns a stack of call frames containing local variables, operand state and return information. Objects and arrays normally live on the shared heap; class metadata lives in metaspace in common JVM implementations.</p><p>This is a reasoning model, not a promise that every local or object occupies one physical location after JIT optimization.</p><div class="concept-table-wrap"><table class="concept-table"><thead><tr><th>Area</th><th>Typical contents</th><th>Ownership</th></tr></thead><tbody><tr><td>Java stack</td><td>Frames and locals</td><td>Per thread</td></tr><tr><td>Heap</td><td>Objects and arrays</td><td>Shared</td></tr><tr><td>Metaspace</td><td>Class metadata</td><td>Process/JVM</td></tr><tr><td>Native stacks/buffers</td><td>Native execution/data</td><td>Runtime dependent</td></tr></tbody></table></div></article><article class="concept-block"><h3>2. Reachability and collection</h3><p>Garbage collectors reclaim objects that are no longer strongly reachable from GC roots such as live thread stacks and static references. Eligibility does not promise immediate collection.</p><p>Java leaks occur when unused objects remain reachable, often through caches, listeners, ThreadLocals or static collections.</p></article><article class="concept-block"><h3>3. Allocation, generations and JIT</h3><p>Most objects die young, so generational collectors optimize frequent young collections and less frequent old-region work. Exact regions and algorithms vary by selected collector.</p><p>The JIT profiles execution and compiles hot methods. Benchmarks need warm-up, isolation and tools such as JMH; <code>currentTimeMillis</code> around one loop is misleading.</p><div class="concept-note"><strong>Important:</strong> Do not call System.gc as an application memory-management strategy; fix reachability and allocation design.</div></article><article class="concept-block"><h3>4. Diagnostic workflow</h3><p>Start from symptoms and measurements: GC logs, heap usage after collection, allocation rate, latency percentiles and thread state.</p><p>Use heap dumps and dominator/retained-size analysis for leaks; Java Flight Recorder and Mission Control help correlate allocation, GC, locks and CPU.</p></article></section><section class="lesson-section" id="examples"><header class="section-heading"><span>RUNNABLE JAVA</span><h2>Examples Worth Tracing</h2><p>Predict the result before running each program. Then change one value and explain the new behaviour.</p></header><article class="example-card"><header><div><span>EXAMPLE 01</span><h3>Release a collection reference</h3></div><button class="copy-code" type="button" data-copy-example="0">Copy code</button></header><div class="code-wrap"><pre><code>import java.util.*;
public class Program {
    public static void main(String[] args){
        List&lt;byte[]&gt; batches=new ArrayList&lt;&gt;();
        for(int i=0;i&lt;3;i++)batches.add(new byte[1024]);
        System.out.println(batches.size());
        batches.clear();
        System.out.println(batches.size());
    }
}</code></pre></div><footer>clear removes the list&#39;s references. The byte arrays become eligible if no other strong references exist; collection timing is still the JVM&#39;s decision.<pre>Output:

0</pre></footer></article><article class="example-card"><header><div><span>EXAMPLE 02</span><h3>Avoid accidental retained views</h3></div><button class="copy-code" type="button" data-copy-example="1">Copy code</button></header><div class="code-wrap"><pre><code>import java.util.*;
public class Program {
    public static void main(String[] args){
        List&lt;String&gt; source=new ArrayList&lt;&gt;(List.of(&quot;A&quot;,&quot;B&quot;,&quot;C&quot;,&quot;D&quot;));
        List&lt;String&gt; snapshot=List.copyOf(source.subList(0,2));
        source.clear();
        System.out.println(snapshot);
    }
}</code></pre></div><footer>An independent immutable snapshot communicates retention intent rather than exposing a mutable backing view.<pre>Output:
[A, B]</pre></footer></article></section><section class="lesson-section" id="trace"><header class="section-heading"><span>INTERACTIVE LEARNING · PROGRAM TRACE</span><h2>Trace heap after speaking your own version aloud.</p></header><div class="interview-list"><details><summary>1. Stack versus heap?</summary><p>Stacks are per-thread call-frame structures; the heap is shared object storage managed by GC. Optimization can change physical placement.</p></details><details><summary>2. Can Java have memory leaks?</summary><p>Yes. Unneeded objects may remain reachable through long-lived references and therefore cannot be reclaimed.</p></details><details><summary>3. What are GC roots?</summary><p>Starting points for reachability such as live thread references, static fields and JNI handles.</p></details><details><summary>4. Why are microbenchmarks difficult?</summary><p>JIT warm-up, dead-code elimination, constant folding, GC and system noise can dominate naive timing.</p></details><details><summary>5. OutOfMemoryError versus StackOverflowError?</summary><p>OOM indicates allocation/resource exhaustion; StackOverflow indicates excessive call-frame depth, commonly recursion.</p></details></div></section><section class="lesson-section" id="practice"><header class="section-heading"><span>PROGRAMMING PROBLEMS</span><h2>Apply the Concept Independently</h2><p>Use the CodeBhavya online compiler.
